Official and vendor-source findings:

- The board has an ESP32-P4NRW32, 32 MB package PSRAM, external 32 MB NOR flash, and an ESP32-C6-MINI-1U-H8 wireless coprocessor connected through SDIO/control signals.
- The panel is a 4-inch 720×720 IPS display driven by ST7703 over two-lane MIPI-DSI. The current vendor profile uses 480 Mbps per lane, a 38 MHz DPI clock, RGB565 or RGB888, and 720×720 timing with horizontal 50/20/50 and vertical 20/4/20 back/front/sync values.
- Panel reset is GPIO27. Backlight PWM is GPIO26 and the schematic-level backlight enable is GPIO33. The vendor BSP uses inverted 5 kHz, 10-bit LEDC PWM on GPIO26.
- Touch is a five-point GT911 on I2C SDA GPIO7/SCL GPIO8. The current vendor BSP and Arduino examples deliberately do not drive reset or interrupt, probe both legal addresses `0x5D` and `0x14`, and poll touch data. Documentation also identifies a reset route on GPIO23 and an interrupt test point, but the supported software path leaves both unassigned.
- BOOT is GPIO35, shared with RMII TXD1; the display firmware does not initialize Ethernet, so it may use the button, subject to physical verification.
- The P4 has no native radio. Arduino-ESP32 3.3.11 carries the matching hosted-WiFi stack; the P4 host stack and the C6 coprocessor firmware remain a compatibility unit that must be tested on hardware.
- The attached v1.3 silicon requires `ChipVariant=prev3`/the pre-v3 360 MHz profile. It must not receive a post-v3/400 MHz artifact.
- The installed Arduino core exposes FQBN `esp32:esp32:esp32p4`, `FlashSize=32M`, `PSRAM=enabled`, `ChipVariant=prev3`, UART0 upload, and a P4 bootloader address of `0x2000` rather than the C6/S3 `0x0`.
- The existing 720×720 geometry fits neither current frame protocol: a 1,440-byte RGB565 row exceeds the 1,394-byte band payload budget, and a 45×45 tile grid needs 2,025 tile indices while `tile_protocol.h` carries only 10-bit indices and caps the bitmap at 1,024 tiles.

## Architecture decisions

1. **Keep Arduino as the application framework, use ESP-IDF drivers underneath.** Arduino-ESP32 3.3.11 has a real P4 target and preserves this firmware's `WiFi`, `Preferences`, `ArduinoOTA`, `AsyncUDP`, sketch lifecycle, and serial configuration code. Porting the complete application to a parallel native-IDF executable would duplicate networking, NVS, OTA, scheduling, and protocol behavior and create two firmware products to keep synchronized. MIPI-DSI remains an ESP-IDF `esp_lcd` implementation behind the shared panel backend.

2. **Make the existing conceptual split concrete before adding P4.** Introduce separate compile-time platform, panel, and carrier data. Platform data owns chip token, memory tier, network topology, serial identity source, receive-task policy, and build profile. Panel data owns controller, geometry, interface, pixel/timing data, and rotation capability. Carrier data owns the exact wiring and peripherals. An exact target composes one of each; it does not create a microcontroller × panel Cartesian product.

3. **Use exact target `p4-4b` and runtime board token `st7703-4b`.** `chip=esp32p4`, `target=p4-4b`, and `board=st7703-4b` keep processor, artifact, and physical profile distinct. P4 chip detection MUST NOT auto-select this target even while it is the only P4 target in the catalog; P4 is explicitly a multi-display family, so a blank P4 requires an exact target choice.

4. **Add a separate large-tile wire format instead of widening the shipped tile format.** Add capability `CAP_LARGE_TILE_STREAM` at bit 19 and a magic-prefixed `ETL1` datagram. Its 10-byte header is `magic[4], frame_id u16, dirty_tile_count u16, flags u8, reserved u8`; each record is `start_tile u16, run_length u8, codec_flags u8, payload_length u16, payload`. The low two codec bits retain Raw/RLE565/BC1/HalfBC1; another bit marks visible spans. This supports 2,025 tiles and future larger panels without changing or ambiguously reinterpreting the shipped band/tile packets. P4 advertises only the large-tile capability; S3-175 keeps the current tile capability, and every other existing target keeps packed bands.

5. **Route every panel write through a backend facade.** SPI/QSPI remains asynchronous with the existing color-transfer callback. MIPI-DPI/DSI uses its own transfer semantics and persistent scanout buffers. The facade owns initialization, rectangle submission, completion/lifetime handling, orientation transform, and brightness so application modules stop assuming that every panel is SPI DMA. The P4 backend software-rotates square dirty rectangles into staging before DSI submission because the pinned ST7703 driver does not support axis swap and does not provide a complete mirror implementation; it MUST NOT falsely advertise quarter-turn support until all four transforms pass on hardware.

6. **Use the current Arduino hosted-WiFi stack and leave the C6 coprocessor untouched initially.** The P4 target uses ordinary `WiFi` APIs after the core initializes ESP-Hosted/`esp_wifi_remote`. If the factory C6 coprocessor is incompatible, stop and record the host/coprocessor versions; do not silently add or flash a second-chip image. A future C6 update role requires its own target, address, recovery, and safety design.

7. **Use a target-specific 32 MB partition table with two OTA slots.** Add a P4 table with NVS at `0x9000`, OTA data at `0xE000`, app0 at `0x10000`, and an equally sized, 64 KiB-aligned app1, leaving ample unused flash rather than adding an unused filesystem. The exact slot size must be at least 4 MiB and finalized only after the first linked P4 size is known. Bundle addresses come from generated build metadata; the P4 bootloader is `0x2000`.

8. **Use a stable base eFuse identity on P4.** Add a platform identity helper: C6/S3 retain their validated station-MAC behavior; P4 uses the eFuse/default base MAC that esptool reports, because no native WiFi interface exists before the hosted C6 starts. USB onboarding and later CFGSHOW must agree on the same six bytes.

## Known unknowns and stop conditions

- The factory ESP32-C6 coprocessor firmware version and its compatibility with Arduino-ESP32 3.3.11 hosted WiFi cannot be learned through the P4 UART/esptool probe. If hosted initialization fails, stop before modifying the C6 and obtain/record the exact compatible coprocessor image and recovery procedure.
- The official high-level page calls out GPIO23 touch reset, while current supported BSP/example code intentionally configures neither reset nor interrupt. Follow the probed-address polling path first; do not drive GPIO23 until the schematic and attached hardware justify it.
- BL_EN GPIO33 behavior is documented but omitted by the current BSP initialization. Start inactive, assert it only as part of backlight initialization, and verify polarity on the attached board before allowing brightness above the conservative project default.
- ST7703's pinned driver does not support `swap_xy` and warns that X mirror is unsupported. Quarter-turns and 180° therefore require backend raster transformation; withhold `CAP_ROTATE` and NACK unsupported values until physical orientation tests pass.
- DSI draw completion, scanout buffer count, DMA2D behavior, RGB565 byte order, and tearing under simultaneous network writes need hardware measurement. Do not emulate the SPI callback by decrementing the DMA gate before the DSI driver has finished consuming a source buffer.
- The first P4 linked size is unknown. If hosted WiFi, DSI, and ST7703 exceed the planned slot, enlarge both P4 OTA slots equally within 32 MB and update partition tests before flashing; do not drop OTA or use asymmetric slots.
- GT911 raw axis signs, edge range, and release timing need physical calibration. Keep calibration in the 4B carrier/touch profile, never in generic P4 platform code.
- GPIO35 is shared with RMII TXD1. It is usable as BOOT only while Ethernet remains uninitialized; future Ethernet support must arbitrate that carrier conflict explicitly.
- `esp_read_mac(...ESP_MAC_WIFI_STA)` is not a valid architectural identity assumption on a radio-less P4. The eFuse/base MAC must match esptool and remain stable before USB onboarding is enabled.
- The current board exposes a CH343 UART path; macOS device naming may vary between `usbmodem` and `usbserial`, so both patterns need tests and single-device refusal.

## Acceptance criteria
