# ESP32-P4 platform and Waveshare 4B display target

The change adds a sixth exact firmware target with ST7703 MIPI-DSI output, GT911 polling, P4 identity/network handling, ETL1 streaming, dual-slot packaging, and macOS bundle support. The recorded host suites and all six target builds pass, and the tool-side blank-device flow refuses to infer `p4-4b` from `esp32p4`. The implementation does not yet satisfy the architecture acceptance criterion because the firmware maps every P4 build to the 4B carrier and the display/backend selection cannot compose P4 with another existing panel. Required runtime validation is also incomplete: hosted WiFi failed, the streaming and OTA paths could not run, visual/touch behavior was not observed, and no S3 hardware regression check is recorded after moving shared draw paths behind the facade. Watch for: the ignored P4 exact-target selector (**confirmed**), the P4-only ST7703 backend and bypassed platform policy (**confirmed**), complete-frame-only ETL1 drawing under UDP loss (**confirmed design; likely user-visible freeze**), blocked P4 runtime validation (**confirmed**), absent S3 functional evidence (**confirmed**), and missing focused sender/bundle safety tests (**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

The command-line tool models P4 as exact-target-required and passes `-DESPDISP_BOARD_P4_4B`, but firmware never reads that define. `CONFIG_IDF_TARGET_ESP32P4` alone selects `Variant::P4_4B`, so a generic or future P4 build silently inherits the 4B pin map, panel, touch controller, and target identity.

The `PlatformConfig` and `PanelConfig` tables are not authoritative: production still chooses PSRAM, receive transport, identity, serial behavior, and display drivers through chip macros or duplicated `Config` fields. P4 excludes the SPI/QSPI constructors and accepts only ST7703 in its DSI backend, so the documented `p4-185`-style composition cannot be assembled from profiles.

ETL1 draws only after every advertised dirty tile arrives. A missing datagram leaves received tiles pending until a later frame completes; unlike the S3 tile path, there is no timed partial-draw fallback, which is likely to freeze high-motion 720×720 updates on a lossy UDP link.

The evidence supports compilation, host parsing, bundle addresses, and basic P4 boot/identity. It does not support release claims for hosted WiFi, ETL1 streaming, OTA, visual output, touch mapping, transforms, or S3 functional preservation, and the status explicitly labels the P4 network limitation as blocking.

The test additions pin the ETL1 header and packet budget, but do not exercise `FrameSender` capability negotiation or positive P4 bundle/USB safety. Those missing tests leave the new transport-selection and update-safety branches without durable regression coverage.

### P4 chip selection aliases the Waveshare 4B carrier

**Critical — `firmware/libraries/espdisp_board/src/board_config.h` — confirmed.** `COMPILED_VARIANT` becomes `Variant::P4_4B` whenever `CONFIG_IDF_TARGET_ESP32P4` is defined. The build tool passes `ESPDISP_BOARD_P4_4B`, but that symbol has no firmware references. As a result, the firmware-level target boundary contradicts the safe tool boundary: compiling the sketch for any P4 without the exact flag still emits `target=p4-4b`, initializes GPIO27/26/33 and GT911 GPIO7/8, and treats ST7703 as attached.

This blocks the stated acceptance criterion that P4 remain usable with future non-4B panels. Gate `P4_4B` on `ESPDISP_BOARD_P4_4B`, reject a P4 build with no exact board selector, and add compile-time coverage that another P4 selector cannot resolve to the 4B profile.

### Platform and panel profiles are descriptive rather than authoritative

**Critical — `firmware/libraries/espdisp_board/src/display_backend.h`, `panel_init.h`, `panel_init_dsi.h`, `platform_config.h`, `frame_pipeline.cpp`, `net_link.cpp`, and `chip_identity.h` — confirmed.** `PlatformConfig` declares PSRAM, raw-lwIP, identity, serial, and WiFi policy, but the streaming firmware still uses `CONFIG_IDF_TARGET_ESP32S3 || CONFIG_IDF_TARGET_ESP32P4` for buffers and receive transport, a P4 preprocessor branch for identity, and a P4 branch for serial timeout behavior. `useRawLwipReceiveTask`, `identity`, and `serial` are not consumed by production behavior.

The panel split has the same problem. `board::Config` duplicates driver, bus, geometry, clock, mode, offsets, inversion, and shape, and shared SPI code continues to read those carrier fields. On a P4 build, `panel_init.h` excludes the existing SPI/QSPI constructors while `panel_init_dsi.h` rejects every driver except ST7703. The architecture document's concrete P4-plus-ST77916 example therefore requires edits to chip-gated backend code instead of composing `PLATFORM_ESP32_P4`, an existing panel profile, and new carrier wiring.

Make platform policy drive the shared runtime choices, make panel configuration the sole source for panel behavior, and select backend/driver by composed panel interface rather than by P4 chip macros. Chip guards should remain only where the underlying SDK API is unavailable on other chips.

### ETL1 waits forever for complete frames

**Important — `firmware/display_stream/frame_pipeline.cpp` — confirmed design; likely user-visible freeze.** `largePending` receives every decoded run, but `largeFramesCompleted` advances only on `Action::ApplyComplete`, and `serviceLargeTileDraw()` returns whenever that counter is unchanged. One lost record therefore prevents all successfully received records from reaching the display. A later completed frame flushes the accumulated bitmap, but repeated loss during motion can prevent any completion indefinitely; the S3 tile path already contains a timed partial-draw mechanism because this exact complete-frame dependency froze that target under load.

Add a bounded partial-draw deadline for pending ETL1 tiles, with separate complete/partial telemetry, and cover an incomplete frame followed by loss, a later frame, and keyframe healing. Hardware streaming measurements are still required to tune the deadline.

### P4 release behavior is not validated and hosted WiFi is known broken

**Critical — `.agents/tasks/p4-4b-impl-status.md`, `release-notes.md`, and `README.md` — confirmed.** The status records `Req_GetCoprocessorFwVersion` timing out against the factory C6 image. Consequently, network association, mDNS, ETL1 streaming, reconnect, OTA, throughput, packet loss, and tearing were not exercised. The environment also supplied no visual or touch observer, leaving color order, visible corners, physical backlight polarity, touch corners/gestures, and software transforms unverified. The README reports these limitations, but the 1.5.0 release item states that hosted WiFi and large-tile streaming support was added without qualifying the known non-working network path.

Resolve the P4/C6 compatibility unit through a separately reviewed, recoverable coprocessor procedure or a proven compatible factory image, then complete the plan's hardware matrix. Until that evidence exists, release documentation must not present hosted WiFi, streaming, touch, or OTA as working hardware support.

### Shared S3 behavior has compile evidence but no functional evidence

**Important — `.agents/tasks/p4-4b-impl-status.md` and the shared display-facade call sites — confirmed.** All four S3 artifacts compiled and the host suites passed, which establishes compile regression safety. No attached S3 run is recorded after every display write, orientation call, and panel brightness call moved through `display_backend.h`; compilation cannot verify DMA callback timing, controller-specific brightness, visible orientation, or actual SPI/QSPI output.

Record a focused hardware smoke test on the affected S3 profiles, at minimum covering initialization, a full and partial draw, orientation, and brightness. If not every board is available, document the exact profiles tested and leave the untested profiles as explicit release risks.

### New transport and update branches lack focused regression tests

**Important — `mac/ESPDisplaySender/Tests`, `firmware/test/test_band_protocol.cpp`, and `tools/test_espdisp.py` — confirmed.** The Swift additions test ETL1 geometry, one hand-authored packet, packet size, and capability-bit independence. They do not test that `FrameSender` keeps 720×720 on the legacy path before EINF, switches only after bit 19, forces a keyframe on negotiation/orientation change, or leaves 466×466 tile-v1 and band targets byte-compatible. Firmware tests exercise one reassembler completion but not malformed codecs, duplicate/stale/restart behavior, incomplete-frame draw policy, or record-count mismatches.

The macOS bundle suite contains no positive `p4-4b` fixture or assertions for `esp32p4`, bootloader `0x2000`, explicit blank-P4 target choice, `st7703-4b` compatibility, or wrong-chip/wrong-target refusal. The implementation status mentions an independent Swift read of a generated bundle, but that ad hoc check does not protect these paths from regression. Add the focused sender, firmware, bundle, USB-onboarding, and firmware-update tests described by the implementation plan.
